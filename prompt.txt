- Note status transitions, what changes each status, and which transitions are NOT allowed.
- Check transactions, retries, timeouts, locking, and what happens with duplicate or concurrent requests.
- Check validation rules, default values, config properties, and feature flags.
- Compare each business rule in the summary and old FSD against the code, one by one.

Then report:

- A table: | Item | Old FSD | Summary | Code | Status (Match / Conflict / Missing) |
- Behavior found in the code but not mentioned in either document

Then STOP and wait for my answers.

## Writing style guide - choose the RIGHT format for each piece of content

Use PROSE (full sentences) when:
- Explaining purpose, context, or WHY a rule exists
- Describing business background or decisions with trade-offs
- Introducing a section before a diagram or table
Keep paragraphs short (2-4 sentences).

Use DIAGRAMS (Mermaid) when:
- Showing interactions between services or systems -> sequenceDiagram
- Showing a process with branches or decisions -> flowchart
- Showing status transitions -> stateDiagram-v2
- Showing entity relationships -> erDiagram
Every diagram must have 1-2 sentences of prose before it explaining what it shows. Keep diagrams focused; split a large flow into several smaller diagrams rather than one huge one.

Use TABLES when:
- Comparing items with the same attributes (fields, error codes, statuses, config)
- Mapping inputs to outputs or conditions to actions
- Listing fields: | Field | Type | Required | Description | Example |

Use SHORT NOTATION when stating rules and conditions precisely:
- "->" for results or transitions: status = PENDING -> APPROVED
- "=", "!=", ">", "<=" for comparisons: amount > 0
- "AND", "OR", "NOT" in capitals for logic
- "IF ... THEN ... ELSE ..." for conditional rules
Example:
  BR-03: IF claim.status = SETTLED AND callback received again
         THEN ignore callback -> log WARN, return 200
Put notation inside code blocks or inline code so it stays readable.

Use NUMBERED LISTS for ordered steps, BULLETS only for short unordered items.

General rules:
- Every BR and FR must be traceable. Add a reference like (Source: ClassName.methodName) where useful.
- Be precise. Avoid vague words: "properly", "handle", "etc.", "as needed".
- Do not invent behavior that is not in the code. Unknown -> Open Questions.
- Write for both developers and non-technical stakeholders: prose explains, notation and diagrams specify.
