Root cause: wrong matching key in updateClaimPaymentAfterAssessClaim

The method loops through every ClaimPayment in the DB and, for each one, loops through every payment from the UI screen. It decides which screen row belongs to which DB row by matching only policyNo + productType.

That combination is not unique. In claim C500107070 there are two plans with the same product type CLINICAL:

claimPaymentId	planId	productType (product)	Decision from UI
7618119	4156491	CLINICAL (CLINICAL)	10 (Approve)
7618121	4156493	CLINICAL (OPDTelemed)	91

Because both rows match on policyNo + productType, each CLINICAL DB row is updated twice, once with each screen value. The logs show this: claimPaymentId 7618119 and 7618121 each appear twice, once with eligibility=10 and once with eligibility=91. Whichever screen row is processed last wins, so the correct value 10 can be overwritten by 91.

Impact

When a plan that should be approved (10) is overwritten to 91, its approvedAmt is reset to 0. The claim then has no approved amount on the plan it should have paid, and the settlement fails.

Fix

Match on a unique key. planId is unique per claim payment and is already available on both sides (planId[4156491] appears in the UI log), so it should be part of the condition. Stop the inner loop once a match is found:

java
for (ClaimPayment payment : paymentList) {
    for (BenefitDeterminationPaymentListForm screenPayment : screenPayments) {
        String screenPolNo = screenPayment.getPolicyNo().split("/")[0];
        if (payment.getPolicyNo().equals(screenPolNo)
                && Objects.equals(payment.getPlanId(), screenPayment.getPlanId())) {
            ClaimPayment claimPayment = claimPaymentRepository
                    .findClaimPaymentByClaimPaymentId(payment.getClaimPaymentId());
            claimPayment.setEligibility(screenPayment.getClaimsDecision());
            claimPaymentRepository.updateClaimPayment(claimPayment);
            break;
        }
    }
}

If planId has a different type on the two classes (for example String and Long), convert one before comparing. If the screen form also carries claimPaymentId, matching on that is even safer. The commented-out setClaimPaymentId line suggests someone once planned to do that.
